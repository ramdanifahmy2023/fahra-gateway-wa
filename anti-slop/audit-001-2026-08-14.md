# WA Gateway Dashboard: Anti-Slop v2.4.0 Audit 001

Date: 2026-08-14  
Scope: `apps/dashboard`  
Mode: AFTER, audit existing UI before any correction  
Method: source inspection, supplied contrast checker, and public runtime checks on login and brand pages. No dashboard source was modified.

## Severity model

Anti-Slop v2.4.0 maps Hard Gate findings to **HIGH**, Purpose-Gate findings to **MEDIUM**, and Quality Locks to **LOW**. Findings below are candidates for confirmation; where source alone cannot prove fabrication or runtime behavior, that limitation is stated.

## Summary

- **HIGH:** 7 findings
- **MEDIUM:** 5 findings
- **LOW:** 1 finding
- **Total:** 13 numbered findings
- Strongest confirmed findings: forbidden em dashes, sub-44px controls, off-canvas navigation remaining keyboard-focusable, missing form control names, and token-level contrast failures.
- The dashboard has good loading/error/empty coverage for most resource views. It also has real routes for all declared navigation items and real files for the brand download links.

## Runtime evidence

- Public login checked at 1440×900 and 390×844. At 390px there was no horizontal overflow (`scrollWidth=clientWidth=390`).
- The login primary action measured 292×44px, but the password reveal control measured only 20×20px and both inputs measured 40px high, confirming Finding 2.
- Public brand page checked at 1440×900 with no horizontal overflow. Its primary links measured 44–46px high and asset links resolved to real destinations.
- Public 200% narrow-viewport simulation exposed clipping on login and horizontal overflow on Brand: login controls extended to x=242 inside a 195px viewport while the card clipped overflow; Brand measured `scrollWidth=226` against `clientWidth=185`.
- Browser console on login was clean. Brand page had one Cloudflare Insights beacon blocked by the site's Content Security Policy; this is an observability/configuration note, not an Anti-Slop finding.
- Authenticated dashboard runtime could not be inspected because the stored bootstrap credential no longer authenticated. Source and public-page findings remain independently evidenced; authenticated interaction coverage is explicitly deferred.

## Numbered findings

### 1. Forbidden em dashes are shipped in UI copy and downloadable brand copy

- **Likely rule / severity:** R-02, **HIGH** (Hard Gate)
- **Confidence:** High
- **Evidence:**
  - `src/components/features/messages-center.tsx:579` uses em dashes as sentence punctuation in both manual/AI status variants.
  - `src/lib/utils.ts:9` returns an em dash for every missing date, propagating the character throughout tables and detail views.
  - `src/components/features/resource-manager.tsx:499` uses an em dash as a generic missing-value fallback.
  - Additional visible fallbacks occur at `src/components/features/whatsapp-monitor.tsx:144`, `src/components/features/backup-panel.tsx:237`, `src/components/features/logs-viewer.tsx:173`, and `src/components/features/messages-center.tsx:704-706,725,733`.
  - `scripts/generate-brand-kit.mjs:46` generates `public/brand/BACA-DULU.txt:1` with an em dash in its title.
- **Why this is a candidate:** R-02 forbids the em dash character in any shipped text. Even where it represents missing data rather than prose, it is still rendered text under the literal gate.
- **Likely remediation direction:** use a plain missing-value label such as `Tidak tersedia`, or a permitted punctuation character where sentence punctuation is intended.

### 2. Shared control sizing violates the 44px mobile tap-target minimum

- **Likely rule / severity:** R-03, **HIGH** (Hard Gate)
- **Confidence:** High
- **Evidence:**
  - Shared default and icon buttons are 40px high/wide, while small buttons are 32px: `src/components/ui/button.tsx:22-25`.
  - CRUD icon actions explicitly override to 32×32px: `src/components/features/resource-manager.tsx:318-335`.
  - The dialog close control is icon 16px plus 6px padding per side, approximately 28×28px: `src/components/ui/dialog.tsx:39-44`.
  - The login password-visibility control is icon 16px plus 2px padding per side, approximately 20×20px: `src/components/auth/login-form.tsx:94-107`.
  - Mobile shell controls use a 16px icon with 8px padding, approximately 32×32px: `src/components/layout/app-shell.tsx:116-122,194-200`.
  - Sidebar links are fixed at 40px high: `src/components/layout/app-shell.tsx:139-157`.
- **Why this is a candidate:** R-03 explicitly requires 44px minimum tap targets. This is systemic because the shared `Button` primitive establishes smaller defaults.

### 3. Closed mobile navigation remains in the keyboard focus order

- **Likely rule / severity:** R-32, **HIGH** (Hard Gate)
- **Confidence:** High
- **Evidence:**
  - The sidebar is always rendered and is only moved off-screen using `-translate-x-full`: `src/components/layout/app-shell.tsx:89-94`.
  - Its navigation links remain normal focusable `<Link>` elements: `src/components/layout/app-shell.tsx:125-159`.
  - The closed state does not apply `hidden`, `inert`, `aria-hidden`, conditional rendering, or disabled tab stops.
  - Opening/closing is click-only state mutation at `src/components/layout/app-shell.tsx:83-87,116-122,194-200`; no Escape handler, focus transfer, or focus containment appears in the shell.
- **Why this is a candidate:** on a mobile viewport, keyboard users can tab into links that are visually outside the viewport. Opening the drawer also does not move focus into it or provide Escape dismissal, making focus location and visual order diverge.

### 4. Several search, filter, edit, and reply controls lack durable accessible names

- **Likely rule / severity:** R-32, **HIGH** (Hard Gate)
- **Confidence:** High
- **Evidence:**
  - Resource Manager search relies on placeholder text and has no label or `aria-label`: `src/components/features/resource-manager.tsx:242-249`.
  - Group search does the same: `src/components/features/groups-panel.tsx:106-113`.
  - Logs search and level select lack labels: `src/components/features/logs-viewer.tsx:82-102`.
  - Contact Memory search is unlabeled, and edit-dialog `Label` elements are not associated with controls by `htmlFor`/`id`: `src/components/features/contact-memory-center.tsx:87,115-119`.
  - Messages search and JID filter are placeholder-only: `src/components/features/messages-center.tsx:402-435`.
  - The manual reply textarea has only a placeholder and no label or `aria-label`: `src/components/features/messages-center.tsx:647-654`.
- **Why this is a candidate:** placeholders disappear as users type and are not a reliable control label. The contact-memory dialog visibly places labels near controls but does not programmatically associate them, so assistive technology cannot reliably determine each field's name.

### 5. Normal-size text has source-computable WCAG AA contrast failures

- **Likely rule / severity:** R-25, **HIGH** (Hard Gate)
- **Confidence:** High
- **Evidence:**
  - Core colors are defined at `src/app/globals.css:8-24`: background ≈ `#0C0F18`, card ≈ `#121721`, muted foreground ≈ `#929CAB`, destructive ≈ `#CB2A2A`.
  - Placeholder text is `text-muted-foreground/70` on a translucent dark input: `src/components/ui/input.tsx:11`. Compositing the declared tokens gives approximately **3.89:1**, below 4.5:1 for the 14px placeholder text.
  - The sidebar section label uses `text-muted-foreground/70` at 10px: `src/components/layout/app-shell.tsx:129-132`, producing the same sub-4.5 class of pairing.
  - `text-destructive` is used for small text at `src/app/error.tsx:18`, `src/components/features/messages-center.tsx:542`, and `src/components/features/messages-center.tsx:733`. The declared destructive color computes to approximately **3.56:1 on background** and **3.34:1 on card**, below 4.5:1 for these normal-size labels.
- **Method note:** ratios were calculated from the source HSL values using the WCAG 2.x luminance formula, including alpha compositing for the placeholder.

### 6. Input/component boundaries do not meet the Human-skill 3:1 non-text contrast bar

- **Likely rule / severity:** R-25 / C-4, **HIGH** (Hard Gate via R-25 Human supplement)
- **Confidence:** High for inputs; lower for purely decorative card borders
- **Evidence:**
  - `--input` ≈ `#303745`, `--border` ≈ `#2A303C`, and background ≈ `#0C0F18`: `src/app/globals.css:8,22-23`.
  - Shared inputs use `border-input` against `bg-background/70`: `src/components/ui/input.tsx:11`; the input edge is approximately **1.6:1** against the adjacent dark background, below the 3:1 non-text requirement.
  - Shared cards use `border-border/80`: `src/components/ui/card.tsx:11`; the declared border is only approximately **1.36:1** against the card surface before the additional 80% alpha reduction.
  - The same low-contrast border tokens recur in tables and controls, for example `src/app/globals.css:90-99` and `src/components/features/resource-manager.tsx:281-282`.
- **Why this is a candidate:** the Anti-Slop Human skill explicitly requires interactive component boundaries and status indicators to meet 3:1 against adjacent colors. Input boundaries are functional, not optional decoration.

### 7. Public pages clip or overflow at 200% narrow-viewport zoom

- **Likely rule / severity:** R-35 / C-4, **HIGH** (Hard Gate)
- **Confidence:** High for the tested public pages
- **Evidence:**
  - At an effective 195px CSS viewport, simulating 200% zoom on a 390px mobile viewport, the login card measured 155px wide but its password reveal control and submit button extended to x=230 and x=242. The card's `overflow-hidden` treatment clipped the escaped content rather than exposing horizontal scroll.
  - The Brand page at the same effective viewport produced horizontal overflow: `scrollWidth=226`, `clientWidth=185`; its primary CTA and H1 extended to x=226.
  - Screenshot: `plan/2026-08-14-wa-gateway-anti-slop-audit-001/screenshots/login-200pct-narrow-clipping.png`.
- **Why this is a candidate:** the Human supplement requires text to remain usable at 200% without clipping or forced horizontal scroll. Both tested public pages fail that resilience check.
- **Likely remediation direction:** remove rigid minimum content widths, allow labels and controls to wrap or shrink, avoid clipping text containers, and add a 200% zoom regression check at narrow breakpoints.

### 8. Stock grid backgrounds are applied without a documented identity/hierarchy purpose

- **Likely rule / severity:** R-07, **MEDIUM** (Purpose-Gate)
- **Confidence:** High
- **Evidence:**
  - `.surface-grid` is a generic two-axis repeating line grid: `src/app/globals.css:78-84`.
  - It covers the login page at `src/app/(auth)/login/page.tsx:10` and forced-password page at `src/app/(auth)/ubah-password/page.tsx:8`.
  - No adjacent comment, design note, or source rationale states what product-specific identity or hierarchy the grid serves.
- **Why this is a candidate:** R-07 identifies grid/blueprint backgrounds as a Purpose-Gate technique. The established brand palette does not by itself document a reason for the grid motif.

### 9. A large panel shadow is the default on nearly every card-like surface

- **Likely rule / severity:** R-12, **MEDIUM** (Purpose-Gate)
- **Confidence:** High
- **Evidence:**
  - `shadow-panel` is a broad `0 20px 70px rgba(0,0,0,.28)` shadow: `tailwind.config.ts:51-53`.
  - Every shared `Card` receives it unconditionally: `src/components/ui/card.tsx:8-13`.
  - Every shared metric receives it too: `src/components/ui/page.tsx:51`.
  - It is also the default for dialogs and global/auth surfaces: `src/components/ui/dialog.tsx:24-28`, `src/app/error.tsx:17`, `src/app/(auth)/login/page.tsx:12`, and `src/app/(auth)/ubah-password/page.tsx:9`.
- **Why this is a candidate:** R-12 reserves shadow for meaningful elevation. Applying the same large shadow to base cards, metrics, dialogs, auth panels, and the error panel flattens hierarchy, and no elevation reason is documented.

### 10. Glow is distributed across the background, all primary buttons, and every metric

- **Likely rule / severity:** R-13, **MEDIUM** (Purpose-Gate)
- **Confidence:** High
- **Evidence:**
  - The body always renders two large radial color glows: `src/app/globals.css:38-50`.
  - Every default primary button receives `shadow-glow`: `src/components/ui/button.tsx:11-13`; the glow definition is at `tailwind.config.ts:53`.
  - Every Metric adds a blurred colored orb: `src/components/ui/page.tsx:51-60`.
  - The overview renders four Metrics simultaneously plus primary actions: `src/components/features/overview-dashboard.tsx:104-171`.
- **Why this is a candidate:** R-13 caps glow at one or two focus accents. Here it is simultaneously a page background treatment, button default, and repeated card decoration. The green/cyan hues match the brand source, but brand color consistency does not satisfy the dose cap.

### 11. Backdrop blur can exceed the 1–2 element glassmorphism cap

- **Likely rule / severity:** R-10, **MEDIUM** (Purpose-Gate)
- **Confidence:** Medium
- **Evidence:**
  - The dashboard header always uses `backdrop-blur-xl`: `src/components/layout/app-shell.tsx:193`.
  - The Messages chat header adds another `backdrop-blur`: `src/components/features/messages-center.tsx:575`.
  - Opening a shared dialog adds a blurred overlay: `src/components/ui/dialog.tsx:22-26`.
  - The mobile navigation overlay is also blurred: `src/components/layout/app-shell.tsx:82-87`.
  - The login surface separately uses `backdrop-blur`: `src/app/(auth)/login/page.tsx:12`.
- **Why this is a candidate:** on Messages with a dialog open, at least three blur layers are present at once. R-10 sets a 1–2 element cap and treats glass as an accent rather than the character of multiple structural layers.

### 12. Repeated card grids flatten content hierarchy

- **Likely rule / severity:** R-14, **MEDIUM** (Purpose-Gate)
- **Confidence:** Medium
- **Evidence:**
  - The overview renders four identical shared Metric cards in one grid: `src/components/features/overview-dashboard.tsx:111-171`; the Metric implementation fixes the same padding, glow, icon box, and layout for each at `src/components/ui/page.tsx:50-78`.
  - The same page ends with three identical QuickLink cards: `src/components/features/overview-dashboard.tsx:283-310,315-340`.
  - Backup opens with a three-column row of identical `Info` cards: `src/components/features/backup-panel.tsx:151-167,291-310`.
- **Why this is a candidate:** R-14 requires card variation to express real hierarchy, with the hierarchy reason written down. These groups give every item the same size, structure, padding, and visual weight, with no stated hierarchy rationale. This is not a claim that cards are inappropriate; it is a candidate that their uniform treatment is under-justified.

### 13. Major visual decisions and liveliness dials are not documented

- **Likely rule / severity:** R-31, **LOW** (Quality Lock), plus the Delivery Gate liveliness block
- **Confidence:** High for missing documentation
- **Evidence:**
  - No `DESIGN.md`, Design Read, or explicit `ENERGY / RHYTHM / MOTION` declaration exists under the audited dashboard tree.
  - Source search found no one-line purpose statements for the grid, global shadow, glow, blur, repeated cards, or spacing system; the implementation points are `src/app/globals.css:38-50,78-84`, `src/components/ui/card.tsx:11`, `src/components/ui/button.tsx:12`, and `src/components/ui/page.tsx:51-60`.
  - There is genuine brand direction in `src/app/brand/page.tsx:9-24,50-68,123-140`, so this is **not** a claim that the product has no identity or an automatic R-37 failure. The gap is that major implementation decisions and dials are not written down as required by R-31 and the v2.4.0 Delivery Gate.
- **Why this is a candidate:** Anti-Slop v2.4.0 requires one-line reasons for major color/layout/type/spacing/card decisions and explicit liveliness dials. Existing brand tokens provide direction but do not explain why the audited interface uses its grid, glow, blur, shadow, or repeated-card treatments.

## Notable passes / non-findings from static source

- **R-24 navigation:** every item in `src/lib/navigation.ts:18-32` has a corresponding page under `src/app/(dashboard)`.
- **R-26 functionality:** inspected buttons and links generally have real handlers or destinations; no obvious decorative dead CTA was found.
- **R-27 data states:** `ResourceManager`, Messages, Groups, Logs, Backup, WhatsApp/QR, Contact Memory, and Overview all contain explicit loading/error/empty branches. Runtime behavior still needs verification.
- **R-21/R-29 direction and palette:** the dark palette and green/cyan/warning system are documented in `src/app/brand/page.tsx:9-24,50-68,123-140`; a fixed dark theme is therefore not automatically treated as an unjustified dark-mode default.
- **R-23/R-38 assets:** brand assets referenced by `src/app/brand/page.tsx:26-46` exist under `public/brand`; navigation and download links are not obvious ghost content.
- **R-36/C-5 security claims:** backend source supports the audited claims: Argon2 password hashing is implemented in `apps/gateway-api/src/modules/auth.ts`; provider secrets use AES-256-GCM through `packages/shared/src/crypto.ts` and `apps/gateway-api/src/modules/catalog.ts`; encrypted backup and WhatsApp auth-state paths are implemented and tested under `scripts/lib/backup-format.mjs` and `apps/baileys-service/src/encrypted-auth-state.ts`.
- **Dialog keyboard mechanics:** shared dialogs use Radix at `src/components/ui/dialog.tsx:3,7-8,22-46`, which is expected to provide Escape dismissal and focus management. The separate custom mobile navigation remains Finding 3.
